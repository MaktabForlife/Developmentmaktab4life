# M4L V100.3.2

## Purpose

Correct three AdminRecords management defects found after V100.3 deployment.

## Corrections

### 1. Duplicate prevention

The Worker now rejects a new AdminRecords registration when an existing account has the same name after case, surrounding-space, and repeated-space normalisation.

Example duplicates:

- `Main Admin`
- ` main admin `
- `MAIN   ADMIN`

The endpoint returns HTTP 409 with code `DUPLICATE_ADMIN_NAME` and does not increment `NextAdminNumber` or append a row.

### 2. Unique AdminID allocation

`NextAdminNumber` is no longer trusted blindly. Before reserving an ID, the Worker checks all existing AdminRecords IDs and advances until it finds an unused `ADMIN<number>` value.

This prevents a stale SystemConfig counter from creating a second `ADMIN1`, `ADMIN2`, and so on.

### 3. Register Another Admin state

After a successful registration, `submitting` is reset. Selecting **Register Another Admin** now returns to a fresh enabled form instead of leaving the button at `Registering...`.

### 4. Modify-admin picker

Admin selection now uses the account's unique login ID as its stable key rather than relying only on `AdminID`.

Update and PIN-reset requests also send the unique login ID, and the Worker treats it as authoritative. This ensures the correct row is selected even if an earlier V100.3 registration already produced duplicate AdminID values.

## Existing duplicate AdminIDs

V100.3.2 prevents new duplicate IDs and safely targets existing rows by unique login ID. Any duplicate values already present in `AdminRecords` column A should still be corrected manually so every account has a unique AdminID.

After correcting an AdminID, that account's active session will be rejected and the user will need to log in again. Set `NextAdminNumber` to a sensible next value as housekeeping, although V100.3.2 will skip occupied IDs automatically.
