# M4L V100.2 — Reset Both PIN Entries After a Mismatch

## Scope

V100.2 refines the V100.1 create-PIN confirmation flow. It does not change the Worker, PIN hashing, transparent migration, throttling, overwrite protection, or session invalidation.

## Changed behaviour

When the first PIN and confirmation PIN do not match:

1. Both PIN entries are cleared.
2. The confirmation row is hidden again.
3. Focus returns to the first digit of the original create-PIN row.
4. The user sees:

   `PINs did not match. Please create your PIN again.`

5. No request is sent to the Worker and no PIN is created.

This removes any uncertainty about the masked first PIN and makes the user deliberately create and confirm a fresh PIN.

## Successful flow retained

1. Only the first create-PIN row is initially visible.
2. Completing the first four digits reveals the confirmation row.
3. A matching confirmation creates the salted PIN.
4. The setup response logs the user in automatically and opens the appropriate Student or Admin home screen.

## Deployment

Deploy the five frontend files in this package. No Worker deployment is required for V100.2.

The Student and Admin HTML files update the `m4l-auth.js` cache-busting query to `v=100.2`, ensuring installed browsers receive the revised mismatch behaviour.

## Verification checklist

Using a Student or Admin account whose PIN has been reset:

1. Confirm only the first create-PIN row appears initially.
2. Enter a four-digit PIN.
3. Confirm the confirmation row appears and receives focus.
4. Enter a different four-digit PIN.
5. Confirm:
   - both PIN rows are empty,
   - the confirmation row is hidden,
   - focus returns to the first PIN row,
   - the revised mismatch message appears,
   - no setup request is sent.
6. Enter and confirm a matching PIN.
7. Confirm the PIN is created and the user is logged in automatically.
