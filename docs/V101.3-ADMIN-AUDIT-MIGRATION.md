# V101.3 authenticated Admin audit migration

## Purpose

V101.3 records the authenticated staff member and server-generated timestamp
for administrative additions and modifications. It also appends every
successful action to `AdminAuditLog` without copying submitted values into the
log.

The Worker never accepts an Admin name or ID from the browser for auditing. It
uses the credential-bound authenticated session. PINs, hashes, secrets, tokens
and credentials are never stored in `ChangedFields`.

## Required deployment order

1. Make a dated backup of the Google Sheet.
2. Create a sheet named exactly `AdminAuditLog`.
3. Put these exact headers in `AdminAuditLog!A1:I1`:

   `AuditID, DateStamp, AdminID, AdminName, Role, Action, RecordType, RecordID, ChangedFields`

4. Append the audit columns below to the right-hand end of each existing
   header row. Do not move, rename or delete existing columns.
5. Deploy the V101.3 Worker/backend.
6. Deploy `version.json` and `js/version.json` with the frontend release.
7. Run the verification checklist below.

V101.3 deliberately fails an administrative write with HTTP 503 if the audit
log sheet or the required row-attribution columns are missing. Reads remain
available.

## Columns to append

The existing `CreateDate`, `CreatedDate` or `Date` column remains the creation
timestamp. The existing `AssignedDate` serves that purpose in `StudentTasks`,
and `UpdatedDate` serves as the modification timestamp in `WeeklyPlanners`.

### Standard master-data columns

Append these five columns, in this order, to:

- `AdminRecords`
- `StudentRecords`
- `SubjectList`
- `ModuleList`
- `TaskList`
- `SubjectResources`
- `TaskResources`
- `Printable`
- `Video`
- `eBooks`
- `Audio`
- `OtherResource`

`CreatedByAdminID, CreatedByAdminName, ModifiedByAdminID, ModifiedByAdminName, ModifiedDate`

### StudentTasks

Append:

`AssignedByName, CreatedByAdminID, CreatedByAdminName, ModifiedByAdminID, ModifiedByAdminName, ModifiedDate`

`AssignedBy` continues to hold the stable Admin ID and `AssignedDate` remains
the creation timestamp.

### WeeklyPlanners

Append:

`CreatedByAdminID, CreatedByAdminName, ModifiedByAdminID, ModifiedByAdminName`

The existing `CreatedDate` and `UpdatedDate` columns retain their current
meaning.

### Attendance

Append:

`AdminName`

The existing `AdminID` and `DateStamp` columns remain unchanged.

### SystemConfig

`SystemConfig` has no header row. Column E now stores the authenticated Admin
name. Its row layout is:

`SettingKey, SettingValue, UpdatedDate, UpdatedByAdminID, UpdatedByAdminName`

Existing rows may remain blank in column E until System Settings are saved
again. Do not reintroduce ID counters.

## Existing rows

- Do not guess or backfill the creator of an existing record.
- Leave new attribution cells blank for historical rows.
- The first V101.3 modification will populate the three modification fields.
- Newly created rows populate creation identity and date; their modification
  fields remain blank until the record is changed.

## AdminAuditLog rules

- The log is append-only; the application has no edit or delete endpoint.
- `AuditID` uses a collision-resistant UUID and does not need an ID counter.
- `ChangedFields` contains field names only, sorted and de-duplicated.
- Bulk task assignments create one audit event per `StudentTaskID`.
- PIN reset events use the action `PIN_RESET` and never include PIN data.

## Verification checklist

1. Create an Admin record and confirm creation ID, name and date are populated.
2. Modify that record and confirm the creation fields remain unchanged while
   the modification fields are populated.
3. Add and modify one Drive resource and confirm the same behaviour.
4. Register and modify one test student.
5. Assign and verify one student task.
6. Save System Settings and confirm column E contains the Admin name.
7. Confirm corresponding rows appear in `AdminAuditLog` with no submitted
   values, PINs or hashes.
8. Confirm ordinary read screens still load normally.

## Compatibility and rollback

- A pre-V101.3 Worker ignores the appended columns, so rollback does not
  require deleting them.
- `AdminAuditLog` can remain present during rollback.
- No Apps Script deployment, Worker binding or Cloudflare variable is added.
- `TimeTable` and `TeacherAssign` remain unchanged in this release.
- Future Course, TimeSlot and timetable-session sheets will use the same audit
  columns from their first write-enabled release.
