# V104.3 — Request-Level Google Sheets Read Deduplication

## Objective

Prevent duplicate Google Sheets value-range reads inside one Worker request while preserving authoritative per-request authentication/access data and all existing business behaviour.

## Scope

V104.3 operates below feature/business logic in the generic Sheets client. It does not add a feature-specific snapshot API and does not persist data between requests.

```text
Incoming Worker request
        ↓
createRequestEnvironment(env)
        ↓
private Map for this request only
        ↓
SpreadsheetID
        ↓
normalized A1 range → Promise<rows>
```

Course environments are created with `Object.create(requestEnv)`, therefore they inherit the same private request context while overriding only the authenticated Course spreadsheet variables.

## Deduplication rules

1. Cache key boundary is **SpreadsheetID + exact trimmed A1 range**.
2. `readGoogleSheetValues()` stores/reuses one promise per range.
3. `batchReadGoogleSheetValues()` checks the same range map and sends only missing ranges to Google.
4. Batch ranges are inserted into the map before awaiting Google, allowing concurrent helpers to share the same in-flight batch.
5. Duplicate ranges inside one requested batch are fetched once but are returned in the caller's original order.
6. A range returned by a batch can satisfy a later single read; a prior single read can satisfy that range inside a later batch.
7. Different spreadsheets and different A1 ranges remain independent.

## Defensive copies

Rows are copied before being stored/returned. A helper that modifies its returned array cannot alter what a later helper receives from the request cache. Google Sheets values are scalar cell values, so row-level copies preserve the existing payload while protecting the cached row structure.

## Write invalidation

After a successful mutation, all cached value ranges for that spreadsheet are removed from the current request context. This applies to:

- `updateGoogleSheetValues()`
- `appendGoogleSheetValues()`
- `batchUpdateGoogleSheetValues()`
- `batchUpdateGoogleSpreadsheet()`

This deliberately invalidates the whole spreadsheet rather than trying to calculate overlapping A1 ranges. A later read therefore goes back to Google and cannot return pre-write data.

## What is not cached

- Nothing is persisted between Worker requests.
- OAuth access-token caching remains the existing separate isolate-level mechanism.
- Spreadsheet metadata/property reads are not placed in the value-range cache.
- V104.3 does not infer that a row range is covered by a previously loaded whole-column/table range. Exact-range matching avoids subtle differences in headers, failure semantics and returned dimensions.

## Failure behaviour

An in-flight range is represented by the same promise for all callers. If the authoritative Google read fails after the existing retry policy, all consumers of that range receive that failure rather than one helper silently substituting an empty table or initiating an independent duplicate read.

## Acceptance criteria

- Same request + same spreadsheet + same range: one Google value read.
- Concurrent same-range callers: one Google value read.
- Overlapping batch/single calls: Google receives only not-yet-loaded ranges.
- Different request: new Google value read.
- Different spreadsheet: new Google value read.
- Successful write: later same-request read refetches from Google.
- Returned row-array mutation does not modify the cached snapshot.
- Existing V104.2 behaviour/regression remains unchanged.
