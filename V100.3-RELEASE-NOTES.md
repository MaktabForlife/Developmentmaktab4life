# M4L V100.3

## Scope

V100.3 adds two related security and administration improvements:

1. Current account status and permission context are checked against Google Sheets on authenticated requests.
2. ADMIN users can register and modify AdminRecords through a new Worker-backed UI.

## Session revalidation

When `M4L_REQUIRE_CREDENTIAL_BOUND_SESSIONS` is `true` (as configured for both M4L environments), every authenticated request reads the current account row and validates it before the route is authorised.

### Student validation

The Worker now confirms:

- StudentID still matches the token row.
- PINSetup is still enabled.
- The current PIN hash still matches the credential version in the token.
- Active is still true.
- ClassGroup still matches the session.

Changing Active, ClassGroup, PINSetup, or PinHash invalidates the existing Student session on its next authenticated request.

### Admin validation

The Worker now confirms:

- AdminID still matches the token row.
- PINSetup is still enabled.
- The current PIN hash still matches the credential version in the token.
- Active is still true.
- Role still matches the session.
- AssignedGroup still matches the session.

Changing Active, Role, AssignedGroup, PINSetup, or PinHash invalidates the existing Admin session on its next authenticated request. The frontend already handles the resulting HTTP 401 by clearing the stored token and returning the user to login.

No account-row cache was added, so these changes take effect on the next authenticated API request.

## Add / Modify Admins

A new `Admins` option appears under the Admin application's `Add or Modify` screen for users whose current role is `ADMIN`.

The UI supports:

- Registering an Admin, Senior, or Teacher account.
- Selecting an assigned group (`ALL` or another stored group value).
- Listing and searching AdminRecords.
- Modifying name, role, assigned group, and Active status.
- Resetting another Admin user's PIN.
- Copying an Admin personal login link.

New Admin accounts are created with:

- `PinSetup = false`
- blank `PinHash`
- `Active = true`
- a new `ADMIN<number>` ID reserved from `SystemConfig / NextAdminNumber`
- a random 10-character UniqueID

The existing V100 setup flow then creates the salted PIN and logs the new user in after confirmation.

## Access and lockout protections

AdminRecords management is available to `ADMIN` only. `SENIOR` and `TEACHER` sessions receive HTTP 403.

The Worker also blocks:

- changing your own role;
- changing your own assigned group;
- deactivating your own account;
- resetting your own PIN from this management screen;
- removing the last active ADMIN account.

These checks are enforced by the Worker, not only by the UI.

## Architecture

All new AdminRecords operations use direct Google Sheets access through the Worker. No Apps Script CRUD route was restored.

New routing features:

- `admin-management-read`
- `admin-management-write`
- `admin-management-update`

All report `google-sheets` as their only available backend.

## Required existing sheet structure

V100.3 uses the current AdminRecords layout:

- A: AdminID
- B: Username
- C: UniqueID
- D: PinSetup
- E: PinHash
- F: Role
- G: AssignedGroup
- H: Active
- I: CreateDate
- J: LastLogin

No new AdminRecords columns are required.

`SystemConfig` must contain a row whose first column is `NextAdminNumber` and whose second column contains the next positive number to reserve.

## Deployment order

1. Confirm `SystemConfig / NextAdminNumber` exists in development.
2. Delete `backend/src/routes/auth.js` from the development branch.
3. Deploy the V100.3 Worker files to `devrebootworker`.
4. Deploy the V100.3 frontend files to the development Pages branch.
5. Test Admin registration, modification, role/status invalidation, and PIN reset.
6. Repeat for production.

Worker-first deployment is recommended. Existing V100 credential-bound sessions remain valid unless the account's current security fields have changed.
