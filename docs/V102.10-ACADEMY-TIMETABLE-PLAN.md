# V102.10 academy-wide timetable plan

Status: approved direction for the next stage. This document is design only;
V102.9.1 does not create an academy schedule index or change timetable data.

## Decision

M4L will provide one academy-wide timetable that combines the current live
published timetables for all active courses and scheduled global subjects.
Every authenticated account may view the complete academy schedule. Sessions
that belong to the viewer are visually active and interactive; all other
sessions remain visible but muted and read-only.

This decision replaces the earlier deferral of a combined multi-course view.
It does not create timetable limits, availability checks or subscription
conflict rules.

## Viewer relevance rules

The backend, not the browser, calculates whether each session is relevant.
Relevance is the union of the viewer's authorised contexts:

- `GLOBAL_ADMIN`: all academy sessions are relevant.
- Course `ADMIN` or `SENIOR`: all sessions for courses in which that account has
  the corresponding active membership are relevant.
- `TEACHER`: sessions assigned to that teacher's stable central account/course
  identity are relevant.
- `STUDENT`: `ALL` sessions and the Student's enrolled group sessions in each
  authorised course are relevant.
- A direct active global-subject subscription makes that subject's scheduled
  sessions relevant.

An account may match more than one rule. The API should return all matching
reasons so the UI can explain why a session is active.

## Visibility and protected actions

The complete, sanitised academy schedule is visible to an authenticated user.
For sessions that are not relevant to the viewer:

- use muted styling;
- do not return or expose Zoom URLs;
- do not expose protected resource actions;
- do not expose Student lists or operational course records;
- do not allow editing or attendance/progress/planner actions.

For relevant sessions, actions remain limited by the viewer's actual role. A
visible row never grants access by itself.

## Central schedule index

A provisional central `AcademyScheduleIndex` is recommended. It should contain
only display and routing data copied from each course's current immutable live
publication. Development drafts must never enter the index.

Provisional data requirements, not final Sheet headers:

- unique index ID;
- CourseID and immutable course display name;
- PublicationID and version;
- PublishedSessionID;
- subject scope (`COURSE` or `GLOBAL`), subject ID and immutable display name;
- module ID and immutable display name when present;
- day, start time and end time;
- group designation;
- teacher central account/reference and immutable display name;
- current/active state and indexed timestamp;
- a protected Zoom-action reference or `HasZoom` flag.

The safest design is not to store a usable Zoom URL in the central display
index. When `canOpenZoom` is true, a protected endpoint should resolve the
current authorised action after revalidation.

## Publication synchronisation

Publishing a course timetable that is already the live source should update
that course's academy-index rows idempotently. Activating a published source
should populate them; rolling back to `TeacherAssign` needs an explicit legacy
indexing policy before implementation.

Index replacement must be atomic per course/publication. A failed refresh must
not leave a mixture of two publication versions. The source publication remains
authoritative if the index and source disagree.

## API boundary

A proposed authenticated endpoint is:

`GET /api/account/academy-timetable/get`

The endpoint should:

1. derive AccountID from the signed account token;
2. revalidate active `UserAccounts`, `UserCourseAccess` and direct global-subject
   subscriptions centrally;
3. resolve teaching assignments against the current course publications;
4. return the complete sanitised schedule with `relevant`, `canOpenZoom` and
   `relevanceReasons` values calculated server-side;
5. fail closed for protected actions when membership or assignment is unclear.

Neither a URL nor a submitted CourseID, AccountID, group or role grants access.

## Cache isolation and invalidation

Account responses should be keyed by at least `AccountID` plus an
`AcademyScheduleVersion`. The version must change after:

- a course publication becomes live;
- a course is activated/deactivated;
- a course membership or role changes;
- a global-subject subscription changes;
- a scheduled global-subject record changes.

Protected Zoom actions must revalidate current access even when the visible
schedule came from cache.

## User interface

The academy timetable should provide one visible pill/segmented selector with:

- **Academy / All**;
- **My schedule**;
- one option for each authorised course;
- **Global Subjects** when applicable.

The **Academy / All** view shows the complete schedule. Relevant sessions use
normal active styling. Other academy sessions use muted styling and are
read-only. The selector should wrap on compact screens rather than becoming an
undiscoverable horizontal strip.

## Implementation sequence

1. Confirm visibility, naming and Zoom-reference decisions.
2. Finalise central index headers and audit/version rules.
3. Build idempotent publication-to-index synchronisation.
4. Build the fail-closed account academy-timetable endpoint.
5. Build the active/muted timetable UI and source pill.
6. Backfill and validate the current Reboot publication.
7. Create the Aalimiyah course Sheet and test two-course aggregation.
8. Add production migration and rollback rehearsal after V102 is complete.

## Decisions still required before build

- Whether unauthenticated public viewing is ever required; the current plan is
  authenticated viewing only.
- Whether muted sessions display teacher names to all signed-in accounts.
- How global subjects acquire days/times, teachers and Zoom actions.
- Whether legacy `TeacherAssign` can be indexed during rollback or academy view
  pauses for that course until a published source is reactivated.
- The final central tab name and exact headers.

No part of this plan should be treated as deployed behavior in V102.9.1.
