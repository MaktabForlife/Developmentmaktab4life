# V104.4 — Google Sheets Read Metrics & Regression Gate

## Purpose

V104.4 makes the V104 read reductions measurable and regression-safe. It does not change business rules, data ownership or Sheet schemas.

This overlay is built directly on the verified V104.2 Development tree. V104.3 request-level read deduplication is **not** included in this overlay and remains a separate pending optimisation.

## Measured read budgets

The backend integration tests now record actual outbound Google Sheets **GET** requests and enforce these budgets:

| Path / scenario | Sheets API requests | Batch requests | Direct reads | Logical ranges |
| --- | ---: | ---: | ---: | ---: |
| Academy timetable — one published Program | 4 | 3 | 1 | 18 |
| Academy timetable — rolling 7-day load | 4 | 3 | 1 | 18 |
| Attendance report | 1 | 1 | 0 | 2 |
| Student Progress task list | 1 | 1 | 0 | 4 |
| Progress report | 1 | 1 | 0 | 4 |
| Progress detail | 1 | 1 | 0 | 4 |
| TeacherAssign timetable with configured Global Zoom | 2 | 1 | 1 | 5 |
| TeacherAssign timetable requiring tolerant legacy Zoom fallback | 3 | 1 | 2 | 6 |

The Academy metric is intentionally counted at the HTTP-request level:

1. central `UserAccounts` credential-row revalidation;
2. one 13-range Platform `batchGet`;
3. one Program profile/config `batchGet`;
4. one Program published-timetable-source `batchGet`.

The rolling seven-day test is required to have the **same four-request budget** as the normal Academy load. Expanding the browser window to seven days must not multiply Google reads.

## Source-level guardrail

V104.4 also records the remaining V104.2 read-path inventory:

- 23 operational `readGoogleSheetValues()` call sites;
- across 17 source files;
- 15 operational `batchReadGoogleSheetValues()` call sites.

The audit test fails if direct-read call sites/files increase above that baseline or if batch-read usage falls below the baseline. Reductions are allowed without changing the guardrail.

This inventory is a regression boundary, not a claim that all remaining direct reads are defects. Some are deliberately single-range, tolerant or compatibility reads.

## Test-only metrics

Metrics are implemented in the backend test harness. They do **not** add public response fields, user-visible diagnostics, cross-request counters or persistent state to the Worker.

`backend/tests/helpers/sheets-read-metrics.mjs` classifies actual mocked Google Sheets HTTP GETs by spreadsheet, batch/direct request and logical range count.

## Full regression command

V104.4 adds one canonical backend command:

```bash
cd backend
npm test
```

`backend/tests/run-all.mjs` executes every `*.test.mjs` file in an isolated Node process and reports the aggregate pass/fail count. The V104.4 build passes **62/62 backend test files**.

## Transient Google failure policy

V104.4 aligns the Google read client with the agreed failure policy:

- retry only transient `429`, `500`, `502`, `503`, `504` responses;
- **one retry maximum** after the original read attempt;
- bounded backoff/jitter remains in place;
- persistent failure remains an authoritative failure and is never converted to an empty table.

The Google Sheets client regression test verifies that a persistent transient failure stops after exactly two attempts total.

## Compatibility boundary

V104.4 changes no:

- Central Identity or role rules;
- Course/Global Subject FREE/PAID access rules;
- timetable publication or visibility rules;
- Attendance calculations or writes;
- Progress calculations or writes;
- Library permissions;
- Planner behaviour;
- Sheet tab/header/schema requirements;
- data ownership boundaries.

`PlatformConfig!B3` remains `102.0.9` and the Platform workbook remains at 19 required tabs.

## V104.3 status

Request-level read deduplication remains separate. V104.4 does not silently create a module-level, isolate-level or persistent data cache. If V104.3 is continued, it must remain request-scoped and security-safe.
