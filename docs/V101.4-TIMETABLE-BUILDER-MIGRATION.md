# V101.4 Timetable Builder migration

## V101.4.3 refinement

V101.4.3 adds staged development and immutable publication snapshots. Follow
`V101.4.3-TIMETABLE-PUBLICATION-MIGRATION.md` and add the three required tabs
before deploying the Worker. The session UI now has one shared Subject/Module
and one Teacher/Zoom assignment per selected group; the former repeatable
Lessons rows are no longer accepted.

## V101.4.2 refinement

V101.4.2 does not add or change any Google Sheet headers. A new-session dialog
can contain multiple lesson rows. Each row has its own Subject, optional Module,
Teacher, and optional Zoom override; Course, Time Slot, Days, Groups, and Active
state are shared.

One save generates a `TimetableSessions` row for every selected
lesson–day–group combination. The complete request is validated before a single
session-data append. Incomplete or exactly duplicated lesson rows are rejected.
If a teacher or group conflict affects any generated session, the response
identifies the lesson number and subject/module and no requested session rows
are written. Every successful generated row receives its own `AdminAuditLog`
event. Existing sessions continue to be modified individually.

## V101.4.1 refinement

V101.4.1 does not add or change any Google Sheet headers. When creating a new
session, Admin may select multiple days and multiple numbered groups. The
application writes one audited `TimetableSessions` row for every selected
day–group combination after validating the complete set.

`ALL` is selected by itself because it already represents every group.
Existing sessions are still modified individually. Conflicts are reported with
the teacher or group, day, 24-hour time range, and course. If any selected
combination conflicts, no rows from that bulk save are written.

## Purpose

V101.4 introduces an ADMIN-only, desktop-first timetable builder. Admins manage
one course at a time, create course-specific start and end times, and place
audited sessions in a Monday-to-Sunday grid.

The existing `TeacherAssign` and `TimeTable` tabs remain unchanged and continue
to supply the live student and teacher timetable in V101.4. Creating the new
tabs does not change the live timetable.

## Required deployment order

1. Make a dated backup of the Google Sheet.
2. Create the three tabs below with the exact names and header rows.
3. Confirm the existing V101.3 `AdminAuditLog` tab and attribution columns are
   present, and verify the existing curriculum headers listed below.
4. Deploy the V101.4 Worker/backend.
5. Deploy the V101.4 frontend.
6. Open Admin > Timetable Builder and create the first course.

The builder fails closed when a required tab or header is missing. Existing
timetable reads continue to work from `TeacherAssign`.

## Courses

Create a tab named exactly `Courses` with this header row in `A1:I1`:

`CourseID, CourseName, Active, CreatedDate, CreatedByAdminID, CreatedByAdminName, ModifiedByAdminID, ModifiedByAdminName, ModifiedDate`

## TimeSlots

Create a tab named exactly `TimeSlots` with this header row in `A1:K1`:

`TimeSlotID, CourseID, StartTime, EndTime, Active, CreatedDate, CreatedByAdminID, CreatedByAdminName, ModifiedByAdminID, ModifiedByAdminName, ModifiedDate`

Start and end times are stored and displayed as 24-hour `HH:MM` values so they
remain stable when read through the Sheets API.

## TimetableSessions

Create a tab named exactly `TimetableSessions` with this header row in
`A1:P1`:

`SessionID, CourseID, TimeSlotID, DayOfWeek, SubjectID, ModuleID, GroupNo, TeacherID, ZoomLink, Active, CreatedDate, CreatedByAdminID, CreatedByAdminName, ModifiedByAdminID, ModifiedByAdminName, ModifiedDate`

`ModuleID` and `ZoomLink` are optional. A blank Zoom link means the session uses
the `GlobalZoomLink` stored in `SystemConfig`. `GroupNo` is `ALL` or a positive
whole number. `DayOfWeek` is one of `Mon`, `Tue`, `Wed`, `Thu`, `Fri`, `Sat`,
or `Sun`.

## Existing curriculum tabs

No change is required to the confirmed production workbook's `SubjectList`,
`ModuleList`, or `TaskList` headers. V101.4 uses their existing IDs and audit
columns. Before deployment, verify these fields remain present:

- `SubjectList`: `SubjectID`, `SubjectName`, `Active`, `CreatedDate`, and all six
  creation/modification attribution fields.
- `ModuleList`: `ModuleID`, `ModuleName`, `SubjectID`, `SubjectName`,
  `Sort Order`, `Active`, `CreatedDate`, `classgroup`, and all six attribution
  fields.
- `TaskList`: `TaskID`, `SubjectID`, `SubjectName`, `ModuleID`, `ModuleName`,
  `TaskName`, `AudioLink`, `GraphicLink`, `VideoLink`, `PDFLink`, `Active`,
  `CreatedDate`, and all six attribution fields.

The backend reads these headers by name, so their current production order is
retained. `GraphicLink` is treated as the existing visual-resource field.

## Audit and ID rules

- IDs are generated from existing rows and do not use Sheet counters.
- Every successful create or modification records the authenticated Admin ID,
  Admin name, and server-generated date.
- Every successful action appends to `AdminAuditLog`.
- Records are made inactive rather than deleted.
- Historical attribution is never guessed or backfilled.

## V101.4 safeguards

- Course names and course time ranges must be unique.
- End time must be later than start time.
- A time slot with active sessions cannot be deactivated or have its times
  changed until those sessions are made inactive or moved.
- A teacher cannot be assigned to overlapping active sessions, including across
  courses.
- A course group cannot be assigned to overlapping active sessions. `ALL`
  conflicts with every numbered group in that course.
- A module, when selected, must belong to the selected subject.

## Cutover

V101.4 is a builder foundation release. It does not automatically publish its
sessions to the current timetable. After the course model is populated and
verified, a later cutover release will make `TimetableSessions` the read source
and define course selection for students and teachers.
