# V102.10 Platform Sheet migration — schema 102.0.5

This migration is additive. Production V101.1 is untouched. Development V102.9.1 remains the rollback code baseline.

## Required final Platform tabs

V102.10 requires **13** central tabs:

1. `CourseRegistry`
2. `UserAccounts`
3. `UserCourseAccess`
4. `UserGlobalSubjectAccess` — legacy, retained unchanged
5. `GlobalSubjectAccessMatrix` — live current SUBSCRIPTION entitlement
6. `GlobalSubjectAccessPolicy`
7. `GlobalSubjectRuns`
8. `GlobalSubjectList`
9. `GlobalModuleList`
10. `GlobalTaskList`
11. `GlobalResources`
12. `PlatformConfig`
13. `PlatformAuditLog`

Tab order is not operationally significant. Names and headers are exact.

## 1. Back up first

Create a full copy of the Platform Sheet. Record:

- `PlatformConfig!B3` — must still be `102.0.4`;
- `PlatformConfig!B4` — current `GlobalCurriculumVersion`;
- `PlatformConfig!B5` when present — `GlobalResourceDriveRootFolderID`.

Do not change a course Sheet or Apps Script for V102.10. Do not alter or delete the existing `UserGlobalSubjectAccess` tab.

## 2. Create `GlobalSubjectAccessMatrix`

Create a tab named exactly `GlobalSubjectAccessMatrix`.

### Header row

- `A1` = `AccountID`
- `B1` onward = every current `GlobalSubjectList.SubjectID`, exactly once.
- Use SubjectID, **not SubjectName**, as the column identity.
- Do not leave blank columns between SubjectID headers.

`V102.10-GlobalSubjectAccessMatrix-template.csv` contains the fixed A1 header. The dynamic SubjectID headers must come from the live `GlobalSubjectList`.

### Account rows

Starting at `A2`, add exactly one row for every `UserAccounts.AccountID`, including inactive accounts. Do not add names to this matrix; the UI joins names from `UserAccounts`.

For each account/subject cell:

- `TRUE` when the legacy `UserGlobalSubjectAccess` tab has an active row for that exact `AccountID + SubjectID`;
- otherwise `FALSE`.

A convenient one-time Google Sheets formula in `B2` is:

```text
=COUNTIFS(UserGlobalSubjectAccess!$B:$B,$A2,UserGlobalSubjectAccess!$C:$C,B$1,UserGlobalSubjectAccess!$D:$D,TRUE)>0
```

Fill it across all SubjectID columns and down all account rows. Then **copy the completed entitlement area and Paste special → Values only** so the final matrix contains explicit TRUE/FALSE values rather than formulas.

Do not delete or rewrite `UserGlobalSubjectAccess` after this seed. It remains the V102.9.1 rollback source.

## 3. Create `GlobalSubjectAccessPolicy`

Create a tab named exactly `GlobalSubjectAccessPolicy`. Paste the exact A1:J1 header from `V102.10-GlobalSubjectAccessPolicy-template.csv`:

```text
SubjectPolicyID | SubjectID | AccessModel | Active | CreatedDate | CreatedByAccountID | CreatedByAccountName | ModifiedByAccountID | ModifiedByAccountName | ModifiedDate
```

For every existing `GlobalSubjectList` data row create exactly one active policy:

- A `SubjectPolicyID`: `GSPOL-<UUID>`;
- B `SubjectID`: exact existing SubjectID;
- C `AccessModel`: `SUBSCRIPTION`;
- D `Active`: `TRUE`;
- E `CreatedDate`: current ISO timestamp;
- F/G: central AccountID/name performing migration;
- H:J blank initially.

Do **not** create per-user rows for FREE access. If a policy is later changed to FREE, every active central account receives implicit access and the matrix values are simply dormant. If changed back to SUBSCRIPTION, the saved matrix values become effective again.

## 4. Create `GlobalSubjectRuns`

Create a tab named exactly `GlobalSubjectRuns`. Paste the exact A1:M1 header from `V102.10-GlobalSubjectRuns-template.csv`:

```text
RunID | SubjectID | RunName | StartDate | EndDate | Timezone | Active | CreatedDate | CreatedByAccountID | CreatedByAccountName | ModifiedByAccountID | ModifiedByAccountName | ModifiedDate
```

No initial run rows are required. Do not manufacture historical runs. New rows use `GSRUN-<UUID>`, dates `YYYY-MM-DD`, a valid IANA timezone, and EndDate must not precede StartDate.

## 5. Verify the matrix before code deployment

Before pushing V102.10:

- every `UserAccounts.AccountID` appears exactly once in matrix column A;
- every `GlobalSubjectList.SubjectID` appears exactly once in row 1 after A1;
- there are no unknown accounts or unknown subject columns;
- every entitlement cell is explicit TRUE or FALSE;
- existing active legacy subscriptions map to TRUE;
- all other cells are FALSE;
- every existing global subject has one active SUBSCRIPTION policy;
- `PlatformConfig!B3` is still `102.0.4`.

The deployed V102.9.1 Worker ignores all three additive V102.10 tabs, so preparing them first is safe.

## 6. Deploy V102.10 from one GitHub commit

Apply the changed-files overlay and push Pages and Worker changes in one commit. Cloudflare Pages and Worker must deploy from the same commit. Confirm Worker root reports `102.10`.

Do not change the schema marker before both deployments are on V102.10.

## 7. Advance `PlatformConfig!B3`

Only after same-commit V102.10 deployment, change `PlatformConfig!B3` from `102.0.4` to `102.0.5`. Do not manually change `GlobalCurriculumVersion`.

## 8. Validate

Run Platform validation. It must report:

- schema `102.0.5`;
- **13 required tabs**;
- one matrix row per central account;
- one matrix SubjectID column per global subject;
- explicit TRUE/FALSE matrix cells;
- one active FREE/SUBSCRIPTION policy per global subject;
- valid run references, dates and timezones.

Focused checks:

1. Existing SUBSCRIPTION subject is visible to an account whose matrix cell is TRUE and hidden from one whose cell is FALSE.
2. Change a safe test subject to FREE; an active account with matrix FALSE can see/open it.
3. Protected Drive resource for that FREE subject opens successfully.
4. Change the subject back to SUBSCRIPTION; its saved matrix flags become effective again.
5. Toggle a SUBSCRIPTION cell in Global Curriculum → Access Matrix and confirm access changes without changing `GlobalCurriculumVersion`.
6. Create future/current/ended test runs and confirm derived statuses.
7. Ending/deactivating a run does not revoke resources when policy entitlement remains valid.
8. Confirm matrix, policy and run mutations create `PlatformAuditLog` entries.
9. Confirm Weekly Planner, Attendance, Progress and Student Records permissions are unchanged.

## Automatic maintenance after migration

- Creating a new global subject through the V102.10 UI creates a default active SUBSCRIPTION policy and adds its SubjectID as a new matrix column, FALSE for all existing accounts.
- Central account migration creates one matrix row for every newly created central account, FALSE across current subject columns.
- FREE policy changes never manufacture per-user entitlement rows.

## Rollback to V102.9.1

If rollback is required:

1. **First change `PlatformConfig!B3` from `102.0.5` back to `102.0.4`.**
2. Revert the single V102.10 GitHub commit so Pages and Worker return to V102.9.1 together.
3. Confirm Worker root reports `102.9.1`.
4. Leave the three additive V102.10 tabs in place; V102.9.1 ignores them.
5. V102.9.1 resumes using the unchanged legacy `UserGlobalSubjectAccess` table. Therefore rollback restores the pre-V102.10 row-based subscription state; matrix-only entitlement changes made after migration are not read by V102.9.1.
6. A V102.10 FREE subject behaves as subscription-only again under V102.9.1.

If rollback happens before `PlatformConfig!B3` is advanced, leave B3 at `102.0.4` and simply revert the code commit.
