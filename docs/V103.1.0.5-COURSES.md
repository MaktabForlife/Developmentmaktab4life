# V103.1.0.5 — Courses

## Purpose

V103.1.0.5 consolidates Global Course definition, recurring scheduling and publication into one **Courses** workspace while retaining the established draft/published timetable architecture.

It does not implement the V103 unified per-user Access Matrix. It does introduce a Course-level FREE/PAID property that is deliberately separate from user roles.

## Data model

### GlobalSubjectRuns

V103.1.0.5 appends one column:

```text
AccessModel
```

The complete header becomes:

```text
RunID
SubjectID
RunName
StartDate
EndDate
Timezone
Active
CreatedDate
CreatedByAccountID
CreatedByAccountName
ModifiedByAccountID
ModifiedByAccountName
ModifiedDate
AccessModel
```

Course AccessModel is exactly `FREE` or `PAID`.

### FIXED

A FIXED Course stores real Course-delivery dates:

```text
StartDate = YYYY-MM-DD
EndDate   = YYYY-MM-DD
```

These dates describe the current delivery period, not the permanent lifetime of the reusable Course definition.

A later repeated delivery can revise StartDate/EndDate and generate a new dated session set. Earlier published snapshots remain historical records.

### ONGOING

An ONGOING Course stores:

```text
StartDate = blank
EndDate   = blank
```

`Publish From` / `Publish Through` are not written into those fields. They are publication/session-preparation inputs. Saving the schedule generates/ensures exact `GlobalTimetableSessions` within that chosen window; publication then publishes only the selected window.

## FREE / PAID semantics

### FREE

Every active central account has participant access automatically.

No per-user ACCESS row is required merely to receive ordinary FREE Course access.

### PAID

Ordinary access is not automatic.

The final authority will be the V103 unified Access Matrix. V103.1.0.5 is deliberately transitional: until that per-Course matrix exists, PAID participant access requires an explicit existing GlobalSubjectAccessMatrix entitlement for the Course's linked Global Subject.

This transitional rule is fail-closed: a PAID Course does not become free merely because the linked Global Subject policy is FREE.

## Migration

### Why migration is required

V103.1.0.4 GlobalSubjectRuns has 13 columns and Course access was effectively inherited from the linked Global Subject. V103.1.0.5 makes access a Course property, so storage must be added without silently changing existing effective access.

### Safe sequence

1. Deploy V103.1.0.5 code first.
2. The code continues to read both the old 13-column and new 14-column GlobalSubjectRuns shapes.
3. Course writes remain blocked while the 14th column is absent.
4. A GLOBAL_ADMIN opens Global Curriculum → Courses.
5. Click **Prepare Courses**.
6. Preview proposes each Course's initial AccessModel:
   - linked Global Subject currently FREE → Course FREE;
   - otherwise → Course PAID.
7. Confirm migration.
8. Worker rewrites GlobalSubjectRuns with the new header and backfilled values, updates PlatformSchemaVersion to `102.0.9`, and writes a PlatformAuditLog row in one Google Sheets batch.

The migration requires exact commit confirmation `MIGRATE COURSES` at the API layer.

No Platform tab is added. Required tab count remains 19.

## Courses UI

Main columns:

```text
Course Name | Global Subject | Type | Start / Publish From | End / Publish Through | Access | Status | Schedule / Publish
```

- one screen Save stores dirty Course/schedule drafts;
- `+ Add Course` creates an unsaved Course draft;
- new drafts can be discarded locally;
- saved Courses use ACTIVE/INACTIVE rather than hard deletion;
- filters: Active / Archived / All.

## Recurring schedule

Each Course expands to schedule rows:

```text
Days | Start | End | Module | Teacher | Zoom link | ×
```

Teacher may remain blank/TBA.

For FIXED Courses, schedule generation uses Course Start/End.
For ONGOING Courses, schedule generation requires Publish From/Through.

Equivalent sessions can be safely re-ensured for an ONGOING window without duplicating them.

## Publication

Publication is always per Course/Run.

Admin can publish directly from the Course table after Save. The detailed session editor is optional.

The Worker continues to maintain:

- GlobalTimetableSessions development rows;
- GlobalTimetableRunState stage;
- GlobalTimetablePublications;
- PublishedGlobalTimetableSessions snapshots;
- GlobalTimetableSessionLifecycle.

Therefore multiple Courses can have independent current published snapshots simultaneously.

### FIXED publication

Only the active scheduled sessions inside the Course's current Start/End delivery window are selected for the new publication.

### ONGOING publication

Publish must include a valid Publish From/Through window. Only active scheduled sessions inside that range are selected for the publication.

## Session editor

View/Edit Sessions provides direct dated editing without row Save/Reschedule/Delete buttons.

Existing sessions are preserved historically; setting lifecycle status to `CANCELLED` is the removal mechanism. A changed date represents rescheduling in the draft.

The editor offers:

- Cancel all changes
- Save without publishing
- Save & Publish

Academic Calendar annotations are informational only.

## Explicit archive

Passing the EndDate of a FIXED Course does not change Active state.

Only the user's explicit `INACTIVE` selection archives a Course. This is intentional so the same Course definition can be reused/repeated later.

## Central Identity boundary

V103.1.0.5 does not change the V103.1 Identity Link migration or make Access the authoritative contextual role source. Teacher eligibility and the unified `FALSE / ACCESS / TEACHER / SENIOR / ADMIN` matrix remain V103.2+ work.
