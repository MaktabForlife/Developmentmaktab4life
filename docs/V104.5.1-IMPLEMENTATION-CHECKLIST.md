# V104.5.1 — Courses Publish & Session UI Refinement

## Objective

Refine the V104.5 Global Courses workflow so the Courses table is the single, clear publication surface while keeping session editing focused on preparing session details only.

V104.5.1 also completes the agreed optional short description for EXPLICIT dated sessions.

## 1. Course name pill

- Keep Course Name inline-editable in the Courses table.
- Render the Course Name input as a rounded coloured pill rather than a standard white form field.
- Use a soft modern lavender treatment with accessible dark text and a visible focus state.
- Do not use the pill colour as a status indicator.

### Acceptance

- Existing and new Course names remain editable without opening another panel.
- Course Name is visually distinct from metadata fields.
- Keyboard focus remains obvious.

## 2. Course-row action layout

- Replace the plain action buttons with a clear two-level action group.
- `Schedule` uses an edit/pencil icon plus text.
- EXPLICIT Courses show `Sessions` using an edit/pencil icon plus text.
- DERIVED Courses show `Exceptions` using the same visual treatment because normal dated occurrences remain virtual.
- `Publish` is visually stronger and sits separately beside the edit actions.
- Use muted teal for Schedule/Sessions/Exceptions and deep berry for Publish.

### Desktop layout

```text
[ ✎ Schedule ]   [  PUBLISH  ]
[ ✎ Sessions ]
```

DERIVED Courses use `Exceptions` in place of `Sessions`.

## 3. Publish visibility and eligibility

The inline Course-row Publish control is the only Course publishing control.

Show `Publish` only when all of the following are true:

1. the Course has already been saved and therefore has a `RunID`;
2. the Course is `ACTIVE`;
3. the Course has a publishable schedule;
4. the Course row/schedule/window has no unsaved changes;
5. the timetable state is unpublished or has been opened as a saved revision (`DEVELOPMENT`);
6. an ONGOING Course has a valid `Publish From` / `Publish Through` window.

Do not show `Publish` for:

- clean already-published Courses;
- inactive Courses;
- unsaved new Course rows;
- rows with unsaved metadata/schedule/window changes;
- Courses without a publishable schedule;
- ONGOING Courses without a valid publication window.

Saving edits to an already-published Course opens the existing revision path; after that save completes the row is eligible to show Publish again.

## 4. Session workspace

- Add a clear outer border and rounded card treatment to the Course Sessions/Exceptions workspace.
- Remove every publish action from the session workspace.
- Session edit actions are exactly:
  - `Cancel` — discard unsaved session changes;
  - `Save` — persist session changes without publishing.
- Use icon + text treatment:
  - Cancel: close icon, neutral soft-grey surface;
  - Save: save icon, strong teal surface.
- Publishing after session changes is performed only from the inline Course row after the session changes have been saved.

## 5. Optional EXPLICIT session description

Add `SessionDescription` only to materialised/exact session storage:

- optional plain text;
- maximum 400 characters;
- editable in EXPLICIT `Sessions`;
- preserved through exact-session edits/reschedules;
- copied into immutable published session snapshots;
- available to Academy detailed session consumers;
- not part of DERIVED recurring schedule rules.

### Platform schema

V104.5.1 uses Platform schema `102.0.11`:

- `GlobalTimetableSessions` adds `SessionDescription` after `OccurrenceDate`;
- `PublishedGlobalTimetableSessions` adds `SessionDescription` after `OccurrenceDate`.

The controlled migration supports:

- `102.0.9 → 102.0.11`, preserving existing Courses as EXPLICIT;
- `102.0.10 → 102.0.11`, preserving existing DERIVED/EXPLICIT modes and publications.

Required Platform tab count remains 19.

## 6. Non-goals

V104.5.1 must not:

- change DERIVED-vs-EXPLICIT Course architecture;
- change Course access rules;
- change Program timetable behaviour;
- add Program Builder schema;
- add a second publishing endpoint/path;
- introduce persistent caching;
- change data ownership.
