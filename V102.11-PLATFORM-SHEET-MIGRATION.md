# V102.11 Platform Sheet migration — exact-dated Global Timetable

V102.11 starts from the **deployed and validated V102.10 Platform schema `102.0.5`**. It adds four central timetable tabs and one PlatformConfig key. Do not copy global sessions into course Sheets.

The migration is additive. Keep the existing V102.10 access-policy, access-matrix and run tabs unchanged.

## Safe order

1. Back up the complete Platform Sheet.
2. Keep the `PlatformSchemaVersion` value at `102.0.5` while preparing the Sheet.
3. Create all four new tabs below using the exact headers.
4. Add `GlobalTimetableVersion = 1` to the next unused `PlatformConfig` row.
5. Do **not** add timetable data manually. Leave the four new timetable tabs header-only.
6. Commit/push Pages and Worker from the same V102.11 GitHub commit.
7. Confirm Worker root reports `102.11` and Pages is from the same commit.
8. Change the existing `PlatformSchemaVersion` cell from `102.0.5` to `102.0.6` (this is `PlatformConfig!B3` when the deployed V102.10 layout is unchanged).
9. Run Platform validation. It must report `102.0.6`, **17 required tabs**, and `GlobalTimetableVersion = 1` before the first publication.

The deployed V102.10 Worker ignores these additive tabs and the extra config key, so Sheet-first preparation is safe. After V102.11 code is deployed, its new Schedule endpoints still fail closed until `PlatformSchemaVersion` is changed to `102.0.6`; do not use Schedule during the cut-over window.

## 1. `GlobalTimetableSessions`

Create a tab named exactly:

`GlobalTimetableSessions`

Paste this exact header row into **A1:P1**:

| Cell | Header |
|---|---|
| A1 | SessionID |
| B1 | RunID |
| C1 | SubjectID |
| D1 | ModuleID |
| E1 | SessionDate |
| F1 | StartTime |
| G1 | EndTime |
| H1 | TeacherAccountID |
| I1 | ZoomLink |
| J1 | Active |
| K1 | CreatedDate |
| L1 | CreatedByAccountID |
| M1 | CreatedByAccountName |
| N1 | ModifiedByAccountID |
| O1 | ModifiedByAccountName |
| P1 | ModifiedDate |

Leave row 2 onward blank. V102.11 creates `GTS-<UUID>` rows through the Schedule UI.

Rules enforced by the Worker:

- `RunID` must reference one `GlobalSubjectRuns` row.
- `SubjectID` must match that run's subject.
- `ModuleID` is optional but, when present, must belong to the subject.
- `SessionDate` uses `YYYY-MM-DD` and must be inside the run dates.
- `StartTime` and `EndTime` use `HH:MM`; EndTime must be later.
- `TeacherAccountID` is a central `UserAccounts.AccountID`. Course membership is not required.
- `ZoomLink` is optional; when present it must be HTTPS.
- `Active` is TRUE/FALSE.

## 5. Add `GlobalTimetableVersion` to `PlatformConfig`

Find the next completely unused row in `PlatformConfig!A:E` and enter exactly:

| Column | Value |
|---|---|
| A (`ConfigKey`) | `GlobalTimetableVersion` |
| B (`ConfigValue`) | `1` |
| C (`UpdatedDate`) | blank |
| D (`UpdatedByAccountID`) | blank |
| E (`UpdatedByAccountName`) | blank |

Do not create the key twice. Do not use a formula.

Draft generation and draft session edits do **not** change this version. Each successful global-timetable publication increments it by one. V102.12 can use this publication version for academy timetable cache invalidation.

## 6. Schema cut-over

Before code deployment:

- `PlatformSchemaVersion` remains `102.0.5`.
- Four new timetable tabs exist with header rows only.
- `GlobalTimetableVersion` exists exactly once and equals `1`.

After Pages + Worker both report the V102.11 commit:

- Change `PlatformSchemaVersion` to `102.0.6`.
- Run Platform validation.
- Confirm **17 required tabs**.
- Confirm zero global timetable sessions/publications before using Schedule.

## Rollback

If rollback is required after the schema flip:

1. Change `PlatformSchemaVersion` back to `102.0.5` **first**.
2. Revert Pages + Worker together to the previously deployed V102.10 commit.
3. Leave the four V102.11 tabs and `GlobalTimetableVersion` row in place. V102.10 ignores them.
4. Do not delete V102.11 timetable/publication rows unless you have first backed up the Platform Sheet and intentionally choose to discard development data.

This rollback is non-destructive to V102.10 access, runs, Library and protected Drive behavior.
