# V104.5 — Derived-by-default Global Course Scheduling

## Objective

Reduce unnecessary stored Course-session rows by making recurring Course occurrences virtual/derived by default, while preserving an intentional exact-session workflow for workshops and other short offerings.

The key invariant is:

> Store the schedule definition for normal recurrence; store a dated occurrence only when that occurrence itself becomes special or when the Course is intentionally EXPLICIT.

## Independent dimensions

`FIXED` / `ONGOING` describes the Course delivery period.

`DERIVED` / `EXPLICIT` describes how dated sessions are represented.

Examples:

- FIXED + DERIVED: term Course with a fixed current delivery period and recurring weekly rules.
- ONGOING + DERIVED: long-running Course whose Academy occurrences are derived for requested/published windows.
- FIXED + EXPLICIT: four-session workshop/intensive with exact prepared dates.
- ONGOING + EXPLICIT: supported for cases where an Admin deliberately prepares exact dated sessions inside a selected Publish From/Through window.

## Data model

### GlobalSubjectRuns additions

- `ScheduleMode`
- `ScheduleDefinition`

`ScheduleDefinition` is canonical JSON. Each rule contains:

```json
{
  "rulekey": "GCRULE-...",
  "days": ["MON", "WED"],
  "starttime": "09:00",
  "endtime": "10:00",
  "moduleid": "GMOD-...",
  "teacheraccountid": "ACCOUNT-...",
  "zoomlink": "https://..."
}
```

The Admin UI continues to display project-standard times in `13h00` style; stored timetable times remain normalized `HH:MM` values.

### GlobalTimetableSessions additions

- `SessionKind` = `EXPLICIT` or `EXCEPTION`
- `ScheduleRuleKey`
- `OccurrenceDate`
- `SessionDescription` — optional short per-session description, maximum 400 characters

`EXPLICIT` rows have no derived anchor.

An anchored `EXCEPTION` has both `ScheduleRuleKey` and `OccurrenceDate`; these identify the virtual occurrence being replaced. An unanchored `EXCEPTION` is a one-off exact extra session.

Normal derived occurrences do not have a row.

### GlobalTimetablePublications additions

- `ScheduleMode`
- `PublishStartDate`
- `PublishEndDate`
- `ScheduleDefinition`
- `RunName`
- `SubjectName`
- `Timezone`

For DERIVED publication, `ScheduleDefinition` is enriched with immutable `modulename` and `teachername` display values. This prevents later curriculum/account edits from changing the meaning of an old publication.

### PublishedGlobalTimetableSessions additions

- `SessionKind`
- `ScheduleRuleKey`
- `OccurrenceDate`
- `SessionDescription`

DERIVED publications store only `EXCEPTION` snapshots. EXPLICIT publication snapshots preserve the exact session description as immutable marketing/display content. EXPLICIT publications store all exact sessions as `EXPLICIT` snapshots.


## EXPLICIT session descriptions

V104.5.1 adds an optional `SessionDescription` up to 400 characters to an EXPLICIT dated session. The field is edited per exact session in **Sessions**, not on the recurring rule. It is preserved through normal exact-session edits/rescheduling and copied into `PublishedGlobalTimetableSessions` when the Course is published.

Academy exposes the description only in detailed authorised session data; label-only/unsubscribed views do not receive it.

## Publication-control rule

The inline Course row is the single publishing surface. Publish is hidden for inactive Courses, clean already-published Courses and rows with unsaved Course/schedule/window changes. It is shown only when an active Course has a valid saved publishable schedule/window and is unpublished or under a saved revision.

The session workspace contains **Save changes** only. It never publishes. Saving session edits leaves the run in DEVELOPMENT/revision state and the Course row is used to publish when ready.

## Stable virtual identity

A derived occurrence uses:

```text
GDERIVED:<RuleKey>:<YYYY-MM-DD>
```

The stable rule/date anchor lets lifecycle/display logic identify an occurrence without pre-creating a Sheet row.

## DERIVED resolution

For a requested window:

```text
immutable publication ScheduleDefinition
        ↓
derive matching rule occurrences
        ↓
load publication EXCEPTION snapshots
        ↓
replace/suppress matching anchored occurrences
        ↓
add one-off/moved exceptions visible in window
        ↓
return effective dated timetable
```

A cancellation remains represented in the resolved publication with CANCELLED lifecycle state. A moved anchored exception suppresses the original virtual occurrence and appears on its new actual SessionDate.

## Publication semantics

### DERIVED

A publication stores the rule snapshot and only exception rows. `SessionCount` records the number of effective occurrences across the full publish window. A full-window resolver fails closed if the reconstructed count does not equal `SessionCount`.

### EXPLICIT

Existing exact-session publication semantics remain: the publication snapshot row count must equal `SessionCount`.

## Exception mutation rules

- Materialising a normal occurrence creates one `EXCEPTION` source row.
- Duplicate `ScheduleRuleKey + OccurrenceDate` anchors are rejected.
- An anchored occurrence must actually exist under the current recurring rule.
- Editing an exception is checked against virtual derived occurrences as well as other stored exceptions.
- The legacy reschedule endpoint is rejected for `EXCEPTION` rows; moving a derived exception edits that single anchored row instead of creating a second linked row.
- Successful edits still move a published Course to DEVELOPMENT/revision state under the existing publication lifecycle rules.

## Academy delivery

Academy iterates eligible active Courses and resolves each current publication. It no longer depends on grouped normal snapshot rows to discover a DERIVED Course. A DERIVED Course can therefore appear in Academy with zero normal `PublishedGlobalTimetableSessions` rows.

The V104 batching boundary is unchanged: this architectural change does not add a new Platform tab or a new Academy Sheet read.

## Controlled migration: 102.0.9/102.0.10 → 102.0.11

The migration is GLOBAL_ADMIN-only, previewable, and committed with the exact confirmation text:

```text
MIGRATE COURSE SCHEDULING
```

It:

1. extends the four existing tables with the V104.5 columns, including `SessionDescription` on source/published sessions;
2. from `102.0.9`, marks every existing Course and existing source/published session row `EXPLICIT`; from `102.0.10`, preserves the current DERIVED/EXPLICIT modes;
3. backfills publication publish windows/display values from existing immutable snapshots/run data where required;
4. preserves existing session descriptions as blank unless already present;
5. updates `PlatformSchemaVersion` to `102.0.11`;
6. writes an audit row.

It does **not** create a new tab and does **not** convert existing Courses to DERIVED.

## Rollback

A code-only rollback is safe before the schema migration.

After the Platform workbook reaches `102.0.11`, older code must not be run against that workbook shape. Rolling back to V104.5 requires restoring the pre-upgrade `102.0.10` workbook; rolling back past V104.5 requires restoring the corresponding pre-scheduling `102.0.9` workbook as well as the matching code.

## Acceptance cases

V104.5 regression coverage includes:

- DERIVED generation endpoint rejection;
- four virtual Monday occurrences across a fixed September Course;
- first publication with zero normal source/snapshot session rows;
- one cancelled occurrence producing exactly one exception row/snapshot;
- single and batch exception edits blocked from overlapping a virtual occurrence;
- derived exception rejected by legacy reschedule endpoint;
- fixed derived Course Academic Calendar/public-holiday context without source sessions;
- Academy delivery from a DERIVED publication with zero normal snapshot rows;
- EXPLICIT four-session September workshop creating/publishing exactly four dated sessions;
- per-session EXPLICIT descriptions saved independently and retained in all four immutable workshop snapshots;
- inline-only publish control with no session-workspace publish action;
- legacy EXPLICIT publication/regression behavior retained;
- V104.1–V104.4 read optimisation regressions retained.
