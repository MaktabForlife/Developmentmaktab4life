# V102.3 unified account verification

V102.3 proves central authentication and course/role selection without changing
which Sheet serves live application data. It is the security checkpoint between
V102.2 account migration and the later dynamic-routing cutover.

## What is active

- `/account/<uniqueid>` checks one central `UserAccounts` identity.
- An account with no PIN may create and confirm one four-digit PIN.
- Existing migrated PINs continue to work; a valid legacy hash is upgraded to a
  salted PBKDF2 hash on successful login.
- Fresh login selects the highest active authority. Equal highest roles use the
  most recent `LastUsedDate`; without history, one `IsDefault=TRUE` row is
  required.
- The account page lists active authorised course/role contexts. Switching does
  not request the PIN again and always returns a new scoped token.
- GLOBAL_ADMIN opens Platform scope and may switch to every active registered
  course without a UserCourseAccess row.
- Account activity, credential version, membership, role, CourseRecordID and
  course registration are revalidated on every central authenticated request.
- First-time PIN setup and a successful legacy-hash upgrade write a central
  PlatformAuditLog event naming only `AuthenticationCredential`; no PIN or hash
  value is logged.

## Deliberate safety boundary

The V102.3 token has `type=account`. Existing live handlers require the legacy
`admin` or `student` token types, so a central token cannot read or modify course
data yet. The account page clearly reports this verification stage.

Keep these routes operational in V102.3:

- `/admin/<uniqueid>`
- `/student/<uniqueid>`

Do not add redirects from those routes to `/account/` yet. Do not remove the
legacy browser token, legacy account sheets or `GOOGLE_SPREADSHEET_ID`.

## Prerequisites

1. V102.2 is deployed and the Platform Sheet validates successfully.
2. Account migration has been committed with no blockers.
3. `UserAccounts` contains active central accounts and one active GLOBAL_ADMIN.
4. `UserCourseAccess!N1` is `CourseRecordID`.
5. `PlatformConfig.PlatformSchemaVersion` is `102.0.3`.
6. `PlatformConfig.AccountLoginBaseUrl` is the exact HTTPS base ending in
   `/account/` for the environment being tested.
7. The Worker service account can read and write the Platform Sheet.

No new tab, header, variable, secret, binding or Apps Script deployment is
required after V102.2.

## Development deployment order

1. Deploy the V102.3 Worker to `devrebootworker` with `--keep-vars`.
2. Confirm the Worker root reports version `102.3`.
3. Deploy the V102.3 Pages files, including the new `account/`, CSS and script.
4. Open the development personal URL:
   `https://developmentmaktab4life.pages.dev/account/<uniqueid>`.
5. Sign in with the migrated PIN, or complete first-time central PIN setup when
   the central row is marked `PINSetup=FALSE`.
6. Confirm the automatically selected context follows the authority rule.
7. Switch to every authorised course/role and confirm no second PIN is asked.
8. Refresh the page and confirm the scoped central session is restored.
9. Deactivate a test membership, refresh, and confirm that context is rejected.
10. Confirm the existing Admin and Student links still sign in and operate.

Use test accounts for revocation checks. Do not deactivate the only active
GLOBAL_ADMIN.

## Expected browser storage

V102.3 uses separate keys:

- `m4l_account_token`
- `m4l_account_context`

Legacy `maktab_token` and `maktab_user_type` keys are not overwritten. Logging
out of the account page removes only the two central account keys.

## Expected API surface

| Endpoint | Purpose |
| --- | --- |
| `/api/account/check` | Validate the personal link and report PIN setup state |
| `/api/account/setup-pin` | Create the first central PIN and sign in |
| `/api/account/login` | Authenticate centrally and select the fresh-login context |
| `/api/account/session` | Revalidate and restore the current central context |
| `/api/account/switch-context` | Revalidate the requested context and issue a new token |

Structured account/context response fields do not expose PIN hashes,
SpreadsheetIDs, AccountIDs, CourseRecordIDs, row numbers or membership IDs.
The signed session token necessarily carries internal binding claims and must be
handled as a credential; it is not an encrypted data container.

## Rollback

Revert the Worker and Pages deployment to V102.2. Central account rows and any
updated `LastLoginDate`, `LastUsedDate` or upgraded PIN hash may remain. Legacy
Admin and Student routes were not redirected or modified, so they remain the
operational rollback path.

## Next release boundary

The next implementation must resolve the authenticated CourseID through
`CourseRegistry`, bind the resolved SpreadsheetID to the request internally,
normalize central account roles into the existing authorization layer and add
CourseID to all relevant cache keys. Only after those routes pass isolation and
permission tests should the Account page launch the operational workspaces and
the legacy URLs begin redirecting.
