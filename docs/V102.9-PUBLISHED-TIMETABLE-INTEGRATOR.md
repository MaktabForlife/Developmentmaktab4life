# V102.9 — Published timetable integrator

## Purpose

V102.9 makes the Timetable Builder's current publication available as the
authoritative live timetable for one selected course. The change is explicit,
course-local and reversible. Deploying the code does **not** switch the source.

`TeacherAssign` remains live until an ADMIN reviews the current publication and
types the activation phrase. `TimeTable` and `TeacherAssign` are not deleted in
this release.

## Schema boundary

- Platform schema remains `102.0.4`.
- Reboot course schema moves from `101.4.3` to `101.4.4` only after the six
  headers below are added.
- No Platform tab is added or removed.
- No account, access, curriculum or subscription migration is run.
- Do not rerun the V102.3 account migration.

## Exact Google Sheet cells

Open the **Reboot course Sheet**, then open `PublishedTimetableSessions`.
Enter these six header values in row 1:

| Cell | Exact value |
| --- | --- |
| `PublishedTimetableSessions!O1` | `CourseName` |
| `PublishedTimetableSessions!P1` | `StartTime` |
| `PublishedTimetableSessions!Q1` | `EndTime` |
| `PublishedTimetableSessions!R1` | `SubjectName` |
| `PublishedTimetableSessions!S1` | `ModuleName` |
| `PublishedTimetableSessions!T1` | `TeacherName` |

Do not type anything into O2:T. Existing historical rows may remain blank in
those columns. V102.9 fills the six values when it creates each new immutable
publication snapshot.

Next open the **Platform Sheet** and update the Reboot row in `CourseRegistry`:

- In the currently supplied development Platform Sheet, Reboot is `COURSE1` on
  row 2, so change `CourseRegistry!E2` from `101.4.3` to `101.4.4`.
- Before editing E2, confirm `CourseRegistry!A2` is still `COURSE1`. If the row
  has moved, update column E on the row whose column A is `COURSE1` instead.

Do not change `PlatformConfig` or its `PlatformSchemaVersion`; it stays
`102.0.4`.

## `TimetableLiveSource`

V102.9 uses one course-local `SystemConfig` key:

- `TEACHER_ASSIGN` — legacy source and default when the key does not exist.
- `PUBLISHED_TIMETABLE` — the current immutable publication is live.

Do not create this row manually. The Admin integration dialog creates or
updates it and writes the corresponding `AdminAuditLog` row atomically.

## Safe deployment order

1. Back up the Platform Sheet and Reboot course Sheet.
2. Apply the V102.9 modified-files overlay to the V102.8.2 development repo.
3. Commit and allow Cloudflare Worker and Pages to deploy from the same commit.
4. Confirm the Worker root reports `102.9` before changing Sheet headers.
5. Add O1:T1 exactly as listed above.
6. Update the Reboot `CourseRegistry.SchemaVersion` cell to `101.4.4`.
7. Open `/account/<uniqueid>`, sign in as an ADMIN and load Timetable Builder.
8. Confirm normal Builder data loads and the integration review reports the
   immutable columns ready.
9. Publish a **fresh** timetable version. This is essential: older snapshots do
   not contain immutable display values.
10. Choose **Review Live Integration**. Review the publication and the
    TeacherAssign comparison.
11. Test the new publication while `TeacherAssign` is still live.
12. When ready, type `ACTIVATE PUBLISHED TIMETABLE` exactly and activate.

Cloudflare may finish Pages before or after the Worker. V102.9 accepts the old
14-column snapshot header for ordinary Builder reads and edits during this
window, but it will block publication and activation until O1:T1 are present.

## What activation changes

Activation changes only the selected course's `SystemConfig` source. It does
not copy or delete timetable rows.

After activation:

- Student timetable reads use the authenticated student's group.
- TEACHER reads remain restricted to that teacher's AdminID.
- ADMIN and SENIOR/SENIOR TEACHER oversight remains unchanged.
- Weekly Planner teacher filtering uses the same published source.
- Per-session Zoom overrides come from the immutable snapshot.
- The course-default `GlobalZoomLink` remains operational and can be rotated
  without republishing.
- A draft edit changes the Builder state to `DEVELOPMENT`, but the last current
  publication remains live until the next publish.
- The next successful publish becomes live immediately.
- The current browser's course-scoped timetable cache is cleared after source
  changes and after a publication that becomes live immediately.

If the current publication pointer, row count, headers or display values become
invalid after activation, the endpoint returns a clear 503 and does not fall
back to `TeacherAssign`.

## Comparison rules

The preview compares logical timetable assignments using:

- day;
- start time;
- subject ID;
- module ID;
- group;
- teacher ID; and
- session Zoom override.

Differences do not automatically prevent activation because they may be
intentional Builder corrections. Snapshot integrity, the current publication
pointer, the expected row count and immutable display values are mandatory.

## Rollback

To return the live course to the legacy source while V102.9 is deployed:

1. Open **Timetable Builder → Review / Roll Back**.
2. Type `RETURN TO TEACHERASSIGN` exactly.
3. Confirm the Admin audit row and test Student/Teacher timetable views.

This rollback does not delete publication history.

If the V102.9 code itself must then be reverted to V102.8.2:

1. Return to `TeacherAssign` first using V102.9.
2. Export or back up `PublishedTimetableSessions`.
3. Remove columns O:T or restore the pre-V102.9 course Sheet backup, because
   V102.8.2 expects the exact A:N header.
4. Restore the Reboot `CourseRegistry.SchemaVersion` to `101.4.3`.
5. Revert the single V102.9 source commit and wait for both Cloudflare
   deployments.

Production remains stable at V101.1 and is not changed by this development
release.
