# V104.2 Program Batch Reads

## Purpose

V104.2 continues the Google Sheets read-optimisation phase started in V104.1. It reduces Google Sheets API request count inside Reboot/Program workbooks while preserving the same data, permissions, publication rules, failure behaviour and Sheet schemas.

No persistent cache, KV, D1 or cross-request identity cache is introduced.

## Academy Home — Program timetable

V104.1 reduced the Platform side of `/api/academy/timetable` to one 13-range Platform `batchGet`, but a published Program still required four Program requests for a GLOBAL_ADMIN and up to six for mixed local roles.

V104.2 splits each Program load into two purpose-specific batches:

1. **Program profile/config batch**
   - `SystemConfig`
   - `StudentRecords` only when student membership must be verified
   - `AdminRecords` only when staff membership must be verified

2. **Selected timetable-source batch**
   - Published source: timetable state + publication + published session snapshot
   - Legacy TeacherAssign source: TeacherAssign + AdminRecords when not already loaded + SubjectList + ModuleList

This deliberately uses two Program requests instead of blindly loading both timetable sources in one oversized batch. It preserves support for Programs that may not contain unused source-specific tabs and avoids unnecessary payload transfer.

In the Academy integration fixture used since V104.1:

| Layer | Before V104.1 | V104.1 | V104.2 |
|---|---:|---:|---:|
| Central credential revalidation | 1 | 1 | 1 |
| Platform Academy state | 13 | 1 | 1 |
| One published Program | 4 | 4 | 2 |
| **Total** | **18** | **6** | **4** |

V104.2 therefore reduces that measured request shape by another 33.3% from V104.1, and by 77.8% from the V103.1.0.5 pre-optimisation baseline.

For student/staff Program access, the local operational identity row is included in the first Program batch rather than fetched separately.

## Reboot timetable reads

The legacy TeacherAssign timetable read now fetches these required tables together:

- TeacherAssign
- AdminRecords
- SubjectList
- ModuleList

The published snapshot path was already batched in the previous architecture and remains so.

`SystemConfig` remains a separate first read because its `TimetableLiveSource` value determines which timetable source is authoritative. The optional legacy `TimeTable` Zoom-link fallback also remains a separate tolerant read so a missing obsolete tab cannot make the current timetable fail.

The global Zoom-link update path now reads TeacherAssign, AdminRecords, SubjectList, ModuleList and SystemConfig in one batch before applying its existing write/audit logic.

## Progress

Student task, Progress report and Progress detail reads previously loaded four Program tables independently. Each now uses one `batchGet` for its required four ranges.

Missing required Sheet behaviour is preserved: a batch failure identifying a missing range still returns the same missing-Sheet response rather than treating missing authoritative data as empty.

## Attendance

The Attendance report now reads `StudentRecords` + `Attendance` in one batch rather than two independent reads. Existing Attendance-header repair behaviour is preserved after the batch returns.

Attendance mark/save behaviour is otherwise unchanged.

## Library resource management

Resource option and curriculum-placement validation now read:

- SubjectList
- ModuleList
- TaskList

in one Program batch rather than three independent requests.

The cross-resource duplicate Drive-file scan is intentionally not forced into one batch because resource tabs are currently optional/tolerant. A missing optional resource tab must not make unrelated resource management fail.

## Central migration tooling

The V103.1 Identity Link and earlier central account migration snapshot paths now read Reboot `AdminRecords` + `StudentRecords` together in one Program batch. Their preview-first and conflict safeguards are unchanged.

## Safety boundary

V104.2 changes read transport only. It does not change:

- `PlatformConfig!B3` or the 19-tab Platform schema;
- Central Identity links or role semantics;
- Course FREE/PAID rules;
- Program/student/staff visibility;
- timetable source authority or publication state;
- Attendance calculations or writes;
- Progress calculations or writes;
- Library resource permissions;
- planner behaviour.

## Deferred to V104.3

V104.3 will add request-scoped read deduplication so a range already loaded during one Worker request can be reused by another helper in that same request without another Google API call. It will not be a cross-request persistent cache.
