# V103.1 — Central Identity Link

V103.1 is the first component of **V103 — Central Identity**.

Its purpose is deliberately narrow: give every normal Reboot operational user record a permanent link to the already-existing central `UserAccounts.AccountID`, without changing which tables currently drive Reboot login or operational behaviour.

## What changes

V103.1 adds one column to each Reboot operational identity tab when it is not already present:

- `AdminRecords` → append `AccountID`
- `StudentRecords` → append `AccountID`

The existing `AdminID` and `StudentID` remain unchanged and continue to be used by Reboot attendance, progress, planner, timetable, resources and other operational functions.

`AccountID` identifies the person across the Academy. `AdminID` / `StudentID` continue to identify the current Reboot operational record.

## Authoritative link source

V103.1 never guesses an AccountID from a display name.

For each Reboot row the preview resolves:

1. the Reboot operational record ID (`AdminID` or `StudentID`);
2. the matching `UserCourseAccess.CourseRecordID` for the current Reboot course and current role;
3. the `UserCourseAccess.AccountID`;
4. the matching `UserAccounts.AccountID`;
5. the Reboot `UniqueID` must match the central `UserAccounts.UniqueID`.

Only after those relationships resolve exactly once is the AccountID eligible to be written.

## Preview-first migration

In **Admin → System Settings → Platform Sheet → V103.1 Identity links**:

1. choose **Preview Identity Links**;
2. review blockers, warnings and planned writes;
3. if clean, type the displayed `LINK <COURSEID>` confirmation;
4. choose **Link Reboot Identities**.

The preview token is signed from the source and central identity state. If any relevant data changes between Preview and Commit, Commit is refused and a new Preview is required.

## Safeguards

V103.1 blocks the write when it finds, among other cases:

- a Reboot record without a matching central membership;
- a central membership with the wrong contextual role;
- a central account that does not resolve exactly once;
- a Reboot `UniqueID` that differs from the central identity;
- an existing nonblank Reboot `AccountID` that conflicts with the resolved central identity;
- two Reboot operational records resolving to the same central AccountID;
- an orphan Reboot `UserCourseAccess` membership;
- duplicate `AccountID` headers;
- unnamed data beyond the last Reboot header where `AccountID` would otherwise be appended.

System rows in `StudentRecords` remain excluded.

Existing conflicting AccountID values are **never overwritten automatically**.

## Behaviour intentionally unchanged

V103.1 does **not** switch Reboot operational authority to `UserAccounts`/`Access` yet.

The following remain on their existing V102.12.8 operational paths:

- legacy Reboot login routes;
- attendance;
- progress;
- Weekly Planner;
- Reboot timetable;
- Reboot resources/library;
- student/admin management;
- task assignment.

The new AccountID column is therefore a permanent identity bridge only. Later V103 components can consume it after independent verification.

## Platform workbook

V103.1 adds no Platform tab and changes no Platform Sheet header.

Keep:

- `PlatformConfig!B3 = 102.0.8`
- 19 required Platform tabs

The migration is confined to the two Reboot operational tabs above.

## Audit

A successful link commit writes a `PlatformAuditLog` entry with action:

`LINK_OPERATIONAL_IDENTITIES`

and record type:

`COURSE_IDENTITY_LINK`

The audit records counts only; the preview UI does not expose central AccountID values.

## V103 component boundary

V103.1 = permanent identity link only.

Later components remain:

- V103.2 — unified Access data model
- V103.3 — Academy Access Matrix
- V103.4 — contextual role / teacher resolution
- V103.5 — central identity authority cut-over
- V103.6 — Reboot compatibility verification

V104 remains the generic Program Builder and V105 remains the Reboot migration into that Program architecture.
