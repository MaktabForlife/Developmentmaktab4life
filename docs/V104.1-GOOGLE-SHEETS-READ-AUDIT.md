# V104.1 Google Sheets Read Audit

## Purpose

V104.1 was started after Development began hitting Google Sheets query limits. The objective is to reduce Google Sheets API request count without changing Maktab4Life business rules, permissions, schemas, or user-visible data.

This audit was performed against the complete V103.1.0.5 Development tree before V104.1 changes.

## Static baseline

The V103.1.0.5 Worker contained:

- **53 direct `readGoogleSheetValues()` call sites** across **21 source files**.
- **43 `readPlatformSheet()` call sites**. Some of these are inside table-loader loops and therefore expand to several Google API requests at runtime.
- Only **3 existing `batchReadGoogleSheetValues()` call sites** across **3 source files** before V104.1.

Largest direct-read source hotspots were:

| Source | Direct Google read call sites |
|---|---:|
| `routes/academy-timetable.js` | 10 |
| `routes/timetable.js` | 9 |
| `routes/drive-library.js` | 7 |
| `routes/weekly-planner.js` | 3 |
| `routes/attendance.js` | 3 |
| `lib/auth.js` | 3 |

The static call-site count is not the same as runtime Google API calls. A helper may be invoked several times in one route, and a loop such as `names.map(readPlatformSheet)` expands one source call site into one API request per tab.

## High-priority runtime audit

### Academy Home timetable — V103.1.0.5

After central-token validation, `/api/academy/timetable` loaded these 13 Platform tabs independently:

1. PlatformConfig
2. UserAccounts
3. CourseRegistry
4. UserCourseAccess
5. GlobalSubjectList
6. GlobalSubjectAccessPolicy
7. GlobalSubjectAccessMatrix
8. GlobalSubjectRuns
9. GlobalTimetableRunState
10. GlobalTimetablePublications
11. GlobalTimetableSessionLifecycle
12. PublishedGlobalTimetableSessions
13. AcademyCalendar

That was **13 Google Sheets API reads for Platform state alone** on every timetable refresh.

Program data was then loaded separately for every active Program. For a published Program this currently costs:

- `SystemConfig`: 1 read
- published timetable state/publication/snapshot: 3 reads
- plus up to 2 Program identity reads (`StudentRecords` / `AdminRecords`) for non-Global-Admin contexts

So the current published Program layer is **4–6 reads per active Program**. This is intentionally reserved for V104.2.

### Central account loading — V103.1.0.5

`loadCentralAccountState()` independently read:

- UserAccounts
- PlatformConfig
- UserCourseAccess
- CourseRegistry
- GlobalSubjectAccessMatrix
- GlobalSubjectAccessPolicy
- GlobalSubjectList
- optionally PlatformAuditLog

Typical central login/context construction therefore used **7 Platform reads**, or **8** when audit data was needed.

### Central session revalidation

Central account tokens are deliberately revalidated on every authenticated request.

Before V104.1:

- PLATFORM token: 1 account-row read
- GLOBAL token: account row + 3 Global access/curriculum tab reads = 4 Platform API calls
- COURSE token: account row + CourseRegistry + membership row = 3 Platform API calls

V104.1 batches the 3 GLOBAL full-tab reads. COURSE-token revalidation remains unchanged for later request-level deduplication work.

## V104.1 changes

V104.1 adds `readPlatformSheets()` in `lib/platform-sheet.js`. It:

- validates requested Platform tab names;
- derives the same strict read ranges as `readPlatformSheet()`;
- sends all ranges to Google Sheets through one `values:batchGet` request;
- validates every returned tab with the existing `validatePlatformSheetRows()` rules;
- rejects invalid/duplicate requested tab names rather than silently weakening validation.

Converted in V104.1:

### Academy Home

The 13 Platform tables above now load in **one `batchGet`**.

Integration coverage verifies a Platform-scope Academy timetable request now performs:

- 1 central credential-row read;
- **1 Platform 13-range batchGet**;
- 4 Program reads for the one published Program in the fixture.

That is **6 Sheets API calls total in the fixture instead of 18 before V104.1** — a 66.7% reduction — before Program batching is even implemented.

### Central account state

The 2/7/8 Platform tabs required by account check/login/context loading are now retrieved in **one Platform batchGet** rather than one request per tab.

### GLOBAL central session validation

The Global Access Matrix, Global access policy and Global Subject list are now one batchGet. Together with the credential row, GLOBAL token revalidation drops from **4 Platform API calls to 2**.

## Deliberately deferred

V104.1 does **not** batch Program/Reboot spreadsheet reads. That is V104.2 so the savings can be measured independently.

It also does not introduce a persistent cache, KV, D1, or cross-request identity cache. V104.3 is intended to add request-level deduplication after Platform and Program batch boundaries are stable.

## V104 roadmap after audit

- **V104.1 — Platform batch reads:** Academy startup + central account Platform table groups.
- **V104.2 — Program batch reads:** one purpose-specific batch per Program spreadsheet where possible.
- **V104.3 — Request-level read context:** ensure a range already loaded in the same Worker request is never fetched again.
- **V104.4 — Metrics/regression:** measured read counts for major routes and final business-rule parity verification.

## Safety boundary

V104.1 changes only the read transport. It does not change:

- Platform schema or tab count;
- UserAccounts / Access semantics;
- Reboot identity links;
- Course FREE/PAID logic;
- timetable visibility;
- attendance/progress/planner logic;
- resource permissions;
- publication state.
