# V104.5.3 — Authoritative ONGOING Draft Publication Window

## Objective

Make `Publish From` / `Publish Through` for ONGOING Global Courses authoritative persisted timetable-draft state so saved DERIVED Courses reload consistently and derive/publish from the same window.

## Defect corrected

Before V104.5.3, the ONGOING Course row could display dates that existed only in browser state. `courseDraftFromRun()` reloaded the window as blank, because `GlobalSubjectRuns` intentionally has no ONGOING StartDate/EndDate and `GlobalTimetableRunState` had nowhere to persist a draft publication window.

The visible symptom was a clean saved Course such as Hifz showing:

```text
ONGOING · DERIVED · ACTIVE
Publish From 01-Sep-2026
Publish Through 01-Sep-2026
Recurring rule Mon–Thu 04h00–05h00

Draft · 0 derived occurrences
(no Publish action)
```

The expected result for Tuesday 1 September is one derived occurrence.

## State model

`GlobalTimetableRunState` now contains:

```text
DraftPublishStartDate
DraftPublishEndDate
```

These fields are only meaningful for ONGOING Courses. FIXED Courses continue to use `GlobalSubjectRuns.StartDate` / `EndDate`.

The draft window is separate from immutable publication history. Each publication still stores its own `PublishStartDate` / `PublishEndDate`.

## Save/reload flow

```text
Courses UI
  → main Save
  → /api/admin/platform/global/run/save
  → GlobalTimetableRunState.DraftPublishStartDate/EndDate

Reload
  → /api/admin/platform/global/delivery/get
  → mapCourseRun()
  → courseDraftFromRun()
  → same saved window
  → derived occurrence count / Publish eligibility
```

Both dates may be deliberately blank. If either date is supplied, both must be valid ISO dates and Publish Through cannot precede Publish From.

## Publication integrity

For ONGOING Courses, `/api/admin/platform/global/timetable/publish` resolves the authoritative saved window from `GlobalTimetableRunState`. If the browser supplies dates that differ from saved state, publication fails and the Admin must save first.

This guarantees that the inline Publish action cannot publish unsaved window changes.

## Migration

Target Platform schema: `102.0.12`. Tab count remains 19.

The controlled scheduling migration accepts source schemas `102.0.9`, `102.0.10` and `102.0.11`. For the normal V104.5.2 path (`102.0.11 → 102.0.12`), it adds the two state columns while preserving Course modes and publications.

For an existing published ONGOING Course, the current publication window seeds the two new draft fields. There is no equivalent authoritative source for an unpublished V104.5.2 ONGOING browser-only window; those dates must be entered and saved once after migration.

## Validation

Platform validation enforces:

- both draft dates blank, or both present;
- valid `YYYY-MM-DD` dates;
- Publish Through >= Publish From;
- FIXED Courses do not carry ONGOING draft-window values.

## Acceptance regression

The automated Hifz case uses:

```text
Course Type: ONGOING
Scheduling: DERIVED
Days: Mon Tue Wed Thu
Time: 04h00–05h00
Publish From: 2026-09-01
Publish Through: 2026-09-01
```

After Save and reload it must derive exactly one occurrence on Tuesday 1 September 2026, remain publish-eligible, and publish that exact derived occurrence.
