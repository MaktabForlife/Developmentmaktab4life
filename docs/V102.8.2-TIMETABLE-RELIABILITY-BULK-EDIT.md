# V102.8.2 Timetable reliability and multi-session editing

## Purpose

V102.8.2 is a focused development correction built on V102.8.1. It fixes the
Timetable Builder failure that appeared after one or two Admin edits and adds a
safe way to edit selected sessions together.

Production remains stable at V101.1. This update does not begin the future
multi-course timetable integrator and must not be applied to production.

## Failure diagnosed

The Builder previously fetched its source tabs one request at a time and then
made a separate TaskList request. A load used approximately twenty Google
Sheets reads, while a save followed by a complete reload could use roughly
thirty-five. Repeating one or two edits could therefore exhaust the Google
Sheets per-user read quota in a short interval.

The upstream 429/500/503 failure was then presented as **Course access could
not be validated**. The Worker also returned the asynchronous route promise
without awaiting it inside its error boundary. A rejected route could therefore
bypass the Worker's JSON/CORS response entirely, which Safari displayed as an
opaque CORS 500. Logging out and returning only appeared to fix the problem
because enough time passed for the quota window to recover.

V102.8.2 changes this behaviour as follows:

- all Builder value ranges, including TaskList, are read with one Sheets
  `values:batchGet` request;
- successful session save, bulk update, delete and restore operations update
  the in-memory grid instead of immediately rereading the whole workbook;
- safe GET requests use a bounded three-attempt retry with short exponential
  backoff for 429, 500, 502, 503 and 504 responses;
- a temporary validation failure is returned as HTTP 503 with
  `COURSE_VALIDATION_TEMPORARILY_UNAVAILABLE` and `retryable: true`;
- asynchronous route failures are awaited inside the Worker error boundary so
  even an unexpected 500 retains the normal JSON and CORS headers;
- the browser keeps the authenticated session for network, 429 and 5xx
  failures; only a genuine HTTP 401 invalidates it; and
- a failed reload preserves an already loaded timetable and offers retry
  feedback instead of replacing it with a misleading setup error.

Writes are not automatically retried because a repeated write is not always
safe or idempotent.

## Multi-session editing

An ADMIN can select **Select sessions** from the Timetable grid, choose two to
one hundred active sessions in the current course, and then select **Edit
selected**.

The editor has independent apply controls for:

- Subject and Module together;
- Teacher; and
- Zoom override.

Only checked controls are applied. For Zoom, applying an empty value clears
the per-session override and returns those sessions to the course-default Zoom
link. Choosing **No module** clears the module.

Bulk editing never changes:

- course;
- day;
- time slot;
- group; or
- active/inactive status.

Inactive sessions must first be restored through the existing lifecycle.

## Validation and atomicity

Before any row is written, the Worker validates the complete proposed set:

- every selected session still exists, is active and belongs to the current
  authenticated course;
- the course, time slots, subject, optional module and teacher are active;
- the module belongs to the selected subject;
- a nonblank Zoom override is HTTPS; and
- teacher and group conflicts are checked against existing sessions and among
  all selected sessions after the proposed change.

If any check fails, no selected session is changed. Successful row changes,
the Development-stage mutation when needed, and audit rows are committed in
one Google Sheets `spreadsheets.batchUpdate` request.

Each changed session receives one `BULK_UPDATE` entry in `AdminAuditLog` with
the exact fields changed. A separate timetable-state audit row is included
when the stage changes to Development.

## Publication boundary

Bulk editing changes only `TimetableSessions`. It never rewrites an existing
`PublishedTimetableSessions` snapshot. A change made after publication returns
the course to Development while preserving the current publication pointer.

The live application timetable still reads from `TeacherAssign`. Moving the
published Builder timetable to the authoritative live source and adding the
cross-course timetable integrator remain later work.

## Data and deployment boundary

V102.8.2 requires:

- no Platform Sheet tab or header change;
- no course Sheet tab or header change;
- no data migration or account migration;
- no Worker variable, secret or binding change;
- no Apps Script deployment; and
- no `GlobalCurriculumVersion` change.

Platform schema remains `102.0.4` and the registered Reboot course schema
remains `101.4.3`.

Use the root `UPDATE-TODO.md` for the exact deployment, testing and rollback
sequence.
